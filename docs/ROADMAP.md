# Roadmap

Что не реализовано и планируется (или сознательно отложено). Актуальное состояние того, что уже сделано — [`README.md`](../README.md); исходная спецификация — архив [`docs/archive/TZ.md`](archive/TZ.md).

## Отложено осознанно

- **PrintJob / учёт расхода по печатям.** Таблица `print_jobs` (id, filament_id FK, weight_used_g, printed_at, model_name) — добавится отдельной Alembic-миграцией, когда будет принято решение по дизайну. Модель данных сейчас этому не мешает.
- **Telegram-бот.** Отдельный сервис, дёргающий тот же backend API — не архитектурить так, чтобы это стало невозможным, но не реализовывать без отдельного запроса.
- **Многопользовательский доступ.** Сейчас один пользователь (логин/пароль в `.env`), но JWT-подход этому не мешает.

## Тестирование

Добавлена интеграционная проверка десктопного backend (`backend/tests/test_desktop.py`):
она запускает упакованный `.exe` с временной базой и проверяет доступ, CRUD,
статистику, перезапуск и резервную копию. Проверка включена в ручной desktop-workflow.
Общего регрессионного покрытия веб-версии пока нет; ранее функционал проверялся вручную.

- **Backend:** pytest + `TestClient` (FastAPI) — CRUD, auth-флоу (login/logout/me, 401 без cookie), агрегации `/stats/*` на фикстурных данных. Отдельная тестовая БД (sqlite in-memory или файл), не боевая.
- **Frontend:** Vitest + React Testing Library — как минимум `FilamentForm` (валидация, submit) и `FilamentList` (сортировка/фильтры/инлайн-edit против замоканного API).
- **CI:** прогонять тесты хотя бы на push в `dev`/PR в `main` (GitHub Actions), пока проверка полностью на человеке.

## Незакрытые мелочи

- Общий порог «пора дозаказать» (когда нет подходящего правила в настройках) всё ещё фиксированные 300 г — `LOW_STOCK_THRESHOLD_G` в `backend/app/crud.py`, не настраивается через UI.
- Production JS-бандл фронтенда > 500 KB (варнинг Vite при сборке) — можно вернуться к code-splitting, если станет ощутимо.
- `docs/DEPLOY.md` (firewall, бэкапы, fail2ban) не обкатан на реальном сервере — при первом деплое сверить и поправить по месту.
- **Проработка локального запуска.** `scripts/dev.ps1` (см. README, «Вариант 0») закрыл большую часть боли — одна команда делает `uv sync`, `alembic upgrade head`, `npm install`, поднимает оба сервиса и при первом запуске сама генерирует `SECRET_KEY` и bcrypt-хэш пароля (спрашивает пароль для `admin`, по Enter — `admin`). Остальные грабли, с которыми уже столкнулись, пока не закрыты:
  - два разных `.env` (`backend/.env` для прямого запуска, корневой `.env` для `docker compose`) — дублирование, легко забыть один из них; скрипт создаёт и заполняет только `backend/.env`, Docker-сценарий по-прежнему настраивается вручную;
  - `$` в bcrypt-хэше нужно вручную удваивать для Compose (`$` → `$$`), иначе значение обрежется — задокументировано, но не защищено кодом;
  - интерпретатор PyCharm не подхватывается автоматически, нужна ручная регистрация SDK через GUI;
  - скрипт есть только для Windows/PowerShell, для остальных ОС по-прежнему только ручные шаги.
  Стоит продумать: единый `.env`, seed-скрипт с тестовыми данными, возможно — devcontainer или кросс-платформенный вариант скрипта.
  - *Мысли по конкретным граблям (не решено, направления для обсуждения):*
    - Единый `.env`: `dev.ps1` мог бы дополнительно генерировать и корневой `.env` (с уже задвоенными `$$` в хэше) из тех же вводных при первом запуске — тогда Docker-сценарий не придётся донастраивать руками отдельно, дублирование вводов уйдёт, хотя сами два файла (разный формат для прямого запуска и для Compose) всё равно останутся.
    - Экранирование `$` → `$$`: сейчас это только текст в README, легко забыть. Можно защитить кодом — например, скрипт для Compose-сценария сам подставляет хэш с экранированием вместо просьбы скопировать вручную.
    - Кроссплатформенность: вместо отдельного bash-скрипта — дублирование логики на двух языках — можно рассмотреть один скрипт на Python (uv и так обязательная зависимость), который будет работать одинаково под Windows/macOS/Linux вместо PowerShell-only `dev.ps1`.
    - PyCharm SDK — разовая ручная настройка, низкий приоритет, вряд ли стоит автоматизировать.
- ~~**Автономный офлайн-запуск для не-разработчика.**~~ Сделано и проверено end-to-end (сборка образов, генерация `.env`, логин через API): `scripts/run-local.ps1` + `docker-compose.local.yml` (см. README, «Вариант 0.5») — одна команда, только Docker Desktop на хосте, без Python/uv/npm и без ручной правки `.env`. Хэш пароля считается через сам backend-образ (`docker compose run backend uv run python -c ...`), `$` в хэше экранируется кодом, а не руками. По ходу нашлись и попутно исправлены два скрытых бага в паттерне генерации `.env`, унаследованном от `dev.ps1`: `[RandomNumberGenerator]::Fill()` — статический метод из .NET 6+, которого нет в Windows PowerShell 5.1 (falls back — `[RandomNumberGenerator]::Create().GetBytes()`); и двойное экранирование `$` при чейнинге `-replace` (замена одного `-replace` использовалась как replacement-строка другого `-replace`, а `$$` там — спецсинтаксис .NET, схлопывающий обратно в один `$` — решение: `if/elseif` вместо чейнинга). Заодно поправлен тот же баг с `RandomNumberGenerator.Fill` и в `dev.ps1` (не всплывал только потому, что `backend/.env` там уже существовал). Открытое: скрипт только для Windows/PowerShell (как и `dev.ps1`), порт зафиксирован на `8080`; офлайн-режим (без доступа к Docker Hub при первой сборке) не проверялся.

## Десктоп-версия (прототип Tauri, решение 2026-10-31)

Выбран сценарий: обычный установщик и ярлык, полностью локальная работа без
Docker/Python на компьютере пользователя. База SQLite хранится в папке данных
пользователя отдельно от установки. Предупреждение SmartScreen у неподписанного
установщика пока принимается; ложные срабатывания антивируса — отдельная проверка.

Начат прототип **Tauri + упакованный Python-backend**: `desktop/`,
`backend/desktop_entry.py`, `scripts/build-desktop.ps1`.
Добавлены автоматический выбор loopback-порта, вход через одноразовую локальную
сессию без пароля, миграции, резервные копии перед запуском (последние пять),
блокировка второго экземпляра и остановка backend при закрытии оболочки.
Для сборки установщика добавлен workflow GitHub Actions: ручная сборка из ветки,
а при отправке тега `vX.Y.Z` — сборка, проверка совпадения версий и публикация
GitHub Release с установщиком и SHA256. Workflow пока не запускался на GitHub.
Локально собран автономный backend и проверен его полный цикл работы на временной
базе; frontend прошёл build/lint. После установки MSVC/Windows SDK успешно
собраны оболочка Tauri и NSIS-установщик (около 22 МБ). Текущая версия исходников —
0.3.10 (patch-бамп перед коммитом); добавлен явный выбор бренда из справочника настроек и стартовые 18 брендов
для новых и существующих баз. Реализована ручная проверка GitHub Releases из настроек
десктопа с открытием страницы скачивания в системном браузере. Автоматическая
установка обновлений не реализована. Ранее проверенный установщик имеет версию
0.0.1; установщик 0.3.10 пока не собран, сборку 0.3.7 пользователь запускал самостоятельно.
Установка и запуск
окна пока не проверены: управление приложениями недоступно в текущей сессии.
Microsoft Defender не обнаружил угроз в текущей локальной сборке backend (2026-10-31).
Инструкции и границы прототипа — [`desktop/README.md`](../desktop/README.md).

Упрощено добавление катушки: цена необязательна, покупка/рейтинг/заметки собраны
в сворачиваемый блок. Материал, цвет и вес обязательны; невыбранный бренд заменяется
на базовый «Нонейм» (добавляется отдельной миграцией).
Неизвестная цена хранится как NULL и отличается от бесплатной
катушки (0); в статистике показывается число записей без цены. Добавлена миграция
с сохранением старых сумм; валидация, расчёты и обновление проверены на временных базах.

До готовности: проверить окно/установщик, установку на чистой Windows,
обновление с сохранением базы и удаление без потери данных; проверить Defender;
добавить понятный экспорт/восстановление. Облачные резервные копии — следующий
отдельный этап, полноценная синхронизация изменений между устройствами — после него.

Автономная PWA обсуждалась как альтернатива, но пока не выбрана: требует переноса
логики backend в браузер и хранения базы средствами браузера.

### Предыдущие варианты и основания выбора

Идея на будущее: раз приложение принципиально однопользовательское и личное (см. CLAUDE.md), для локального использования без VPS вообще можно рассмотреть не веб-деплой, а нативное десктоп-приложение — просто установил и пользуешься, без Docker/Caddy/домена/сертификатов.

Варианты, если до этого дойдёт:
- **Tauri + Python-сайдкар.** Лёгкая Rust-обвязка (WebView2 на Windows), фронтенд как есть. Backend паковать через PyInstaller/Nuitka в отдельный exe и запускать как sidecar-процесс при старте приложения, фронтенд стучится на `localhost`. Плюс — маленький размер итогового бинарника; минус — Rust-тулчейн в сборке и чуть более нетривиальная обвязка sidecar-процесса в Tauri.
- **Electron + Python-сайдкар.** Та же схема, но обвязка на JS/Node — более протоптанный путь для питон-сайдкаров (много прецедентов), но бандл тяжелее из-за Chromium.
- **PWA как дешёвый промежуточный шаг.** Installable-приложение поверх уже работающего фронтенда (своя иконка, отдельное окно без адресной строки браузера) — почти бесплатно поверх варианта «офлайн-запуск на localhost» выше, не требует ни Tauri/Electron, ни паковки Python в бинарник. Не даёт трея/автозапуска/полностью нативного ощущения, но закрывает большую часть желания «not-a-browser-tab» малой кровью.

Эти варианты обсуждались до выбора Tauri 2026-10-31. Трей, автозапуск,
кроссплатформенные сборки и цифровая подпись пока не входят в прототип.

## Монетизация (стратегия, решено 2026-10-05)

Репозиторий остаётся публичным; зарабатывать на удобстве и серверных услугах, а не на закрытии кода (модель open core, как у Joplin / Bitwarden).

- **Лицензия — AGPL-3.0** (с v0.3.4, до этого MIT). Выбрана вместо GPL из-за «SaaS-лазейки»: приложение по сути веб-сервис, и под GPL кто-то мог бы поднять закрытый хостинг на его основе. Автор как единственный правообладатель не связан собственной лицензией — может держать закрытый облачный сервер. **Если начнут приходить чужие PR — сначала ввести CLA**, иначе это право на чужой код не распространяется.
- **Очерёдность:**
  0. **Сначала довести программу до состояния, удобного для ежедневного использования** — пока этого нет, распространение и монетизация не начинаются.
  1. Бесплатное распространение по каналам из раздела «Распространение» ниже (Docker / домашние серверы, Tauri-установщик через winget и Scoop); деньги на этом этапе — донаты/Boosty. Цель этапа — проверить спрос.
  2. Если спрос есть — платная подписка на облачные функции отдельным закрытым сервисом.

  *Пересмотрено 2026-10-05:* изначально планировалось продавать готовый установщик (pay-what-you-want), но winget/Scoop/Docker-каналы требуют публичной бесплатной ссылки на сборку, а платный сертификат подписи кода не окупится — поэтому сборки бесплатные, монетизация только через донаты и серверные функции.
- **Правило: платное живёт на сервере, а не в клиенте.** Флажки «есть подписка» в открытом клиенте вырезаются форком за минуты; DRM/ключи активации не делать.
- **Кандидаты в подписку:** синхронизация между устройствами и облачный бэкап; доступ с телефона без своего VPS; Telegram-бот (уведомления «пора дозаказать», списание после печати); позже — мониторинг цен на филамент, общий учёт на несколько человек. Всё локальное (учёт, статистика, остатки) остаётся бесплатным.
- **Учесть до запуска облака:** 152-ФЗ (email аккаунта — персональные данные; локализация данных россиян на серверах в РФ, уведомление РКН); приём рекуррентных платежей (ЮKassa/CloudPayments/Boosty — нужен статус самозанятого/ИП; Paddle/Stripe/Lemon Squeezy для резидента РФ, скорее всего, недоступны — проверить); облачному серверу нужна многопользовательность (сейчас вне scope).

## Распространение (план, отложено до готовности программы — решено 2026-10-05)

Не начинать, пока программа не отточена для повседневного использования. Сертификат подписи кода **не покупать** (порядка $100–400/год — не окупится); все каналы ниже работают без него.

**1. Docker — основной канал, прежде всего для домашних серверов.** Многие 3D-печатники уже держат Raspberry Pi / мини-ПК с OctoPrint/Klipper или Home Assistant.
- Мультиархитектурные образы (amd64 + arm64) в GHCR через GitHub Actions по тегу.
- `run-local.ps1` перевести на готовые образы из GHCR вместо `up -d --build` на каждом запуске — заодно решает запуск без интернета (сейчас сборка на каждом старте лезет в реестры за базовыми образами и без сети может упасть).
- Каталоги в один клик: Home Assistant add-on (можно отдавать остатки филамента как сенсоры HA), CasaOS / Umbrel / ZimaOS, Unraid Community Apps, шаблоны Portainer.

**2. Десктоп для Windows — Tauri-установщик без подписи** (обвязка — см. раздел «Десктоп-версия» выше).
- Без подписи Windows один раз показывает SmartScreen («Подробнее → Выполнить в любом случае») — для технической аудитории приемлемо.
- **winget** — основной Windows-канал: встроен в Windows 10/11, есть GUI-фронтенд UniGetUI. Попадание — PR с YAML-манифестом в `microsoft/winget-pkgs` (генерирует `wingetcreate` / Komac), автопроверка (антивирус + тихая установка в VM) и модерация; первая публикация — от нескольких дней до пары недель, дальше PR открывается из CI автоматически. Требования: тихая установка (NSIS/MSI от Tauri подходят), постоянная ссылка с версией в URL (не `latest`), файл не подменять — в манифесте SHA256. Подпись не требуется; при установке через winget SmartScreen, как правило, не всплывает (файл не получает Mark-of-the-Web).
- **Scoop** — своим bucket'ом (отдельный репозиторий `lastloony/scoop-bucket` с JSON-манифестом, без модерации; `checkver`/`autoupdate` для автообновления). Нужна портативная zip-сборка; данные хранить в `%APPDATA%`, а не рядом с exe. Официальный `extras` для нового проекта — вряд ли.
- Оба канала требуют публичной бесплатной ссылки на сборку — продавать exe параллельно бессмысленно.

**Главный риск — ложные срабатывания антивирусов.** Backend, упакованный PyInstaller'ом, часто детектится Defender'ом (бутлоадер используют и реальные вредоносы); у неподписанного exe шанс выше, и валидацию winget он может не пройти. **Проверить первым делом, до шлифовки Tauri-обвязки:** собрать backend в exe через PyInstaller (с бутлоадером, собранным из исходников) и через Nuitka, прогнать Defender'ом, выбрать более чистый вариант. При срабатывании — заявка о false positive в Microsoft (бесплатно).

**Целевой пайплайн:**
```
git tag vX.Y.Z → GitHub Actions:
  ├─ backend (Nuitka/PyInstaller) + Tauri → setup.exe (NSIS) и portable.zip
  ├─ GitHub Release с обоими файлами
  ├─ PR в microsoft/winget-pkgs (Komac)
  ├─ обновление JSON в scoop-bucket
  └─ мультиархитектурный Docker-образ в GHCR
```

**Если когда-нибудь понадобится подпись:** SignPath Foundation бесплатно подписывает open-source-проекты, собранные из публичного репозитория через CI (условия строгие — проверить совместимость с монетизацией); у Certum есть недорогой сертификат для open-source-разработчиков (доступность для резидентов РФ не проверена). Microsoft Store подписывает сам, но для резидента РФ регистрация/выплаты, скорее всего, закрыты.
